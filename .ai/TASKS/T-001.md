## Finding 2 - Exact Idempotency Contract & Architectural Limitation
**The Contract:** The system must avoid duplicate side-effects (At-Most-Once) where deterministic. However, the system relies on external channels (LinkedIn UI API, simple SMTP) which DO NOT provide client-supplied idempotency keys. 

**Architectural Limitation (Two Generals Problem):**
Because SQLite persistence and external network side effects are not a single atomic operation, absolute At-Most-Once cannot be mathematically guaranteed without changing the DB schema to implement a Pre-Commit Intent Lock (which would result in dropped messages upon crash). 
- `Finding 2a` successfully models this boundary and proves that a crash *immediately* after `sendMessage` but before DB persistence WILL result in a duplicate upon retry. This is an accepted, documented limitation.

**The Feasible Mechanism (Minimal Fix):**
Without changing the schema, we cannot implement a pre-commit intent lock. Our goal is to minimize the crash window and fix the deterministic duplication path (Scenario B: manual Retry after a post-action exception like `saveSessionState`).
1. Move the `INSERT INTO outbound_events` inside `executeStep`, IMMEDIATELY after the network call succeeds. This drastically shrinks the crash window.
2. Add a `SELECT` deduplication check at the top of `executeStep`. If an `outbound_events` row exists for `(run_profile_id, step_id)`, return `SUCCESS` instantly without calling the external service.
This guarantees idempotency against *persisted* successes (fixing manual retries), while explicitly acknowledging the distributed crash vulnerability as a permanent limitation.
