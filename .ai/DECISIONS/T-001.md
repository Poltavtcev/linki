# Decision Record: T-001 (Campaign Engine Targeted Recovery)

## Problem / Contract
Unverified findings from early audits showed severe state machine leaks and deduplication vulnerabilities:
1. **Finding 1:** `failed` states were immune to manual unenrollment/cancellation.
2. **Finding 2:** Lack of idempotency allowed manual retries to duplicate external side-effects (e.g. sending messages multiple times).
3. **Finding 3:** The R3 `delay-routing.test.ts` had a false-confidence failure that masked true system behavior for delay nodes.

## What Changed
- Explicitly added `'failed'` to the state machine transition guards in the 4 cancellation pathways.
- Moved `INSERT INTO outbound_events` inside `executeStep` immediately following the network call to eliminate the async-tick race condition.
- Added a `SELECT` deduplication check at the top of `executeStep` to prevent repeated network calls for the same run_profile and step.
- Rewrote `delay-routing.test.ts` and `characterization-delay.test.ts` to assert the true contract: delay nodes immediately transition to `running` with a `next_eval_at`, rather than instantly completing.

## Risks & Known Limitations
- **Finding 2a (Accepted Architectural Limitation):** The Two Generals Problem exists because Playwright `sendMessage` and SQLite persistence are not atomically linked. If the system crashes *after* external success but *before* the DB insert, a retry will duplicate the message. We have documented this explicit constraint and asserted it in tests (`t001-idempotency.test.ts`).

## Architectural Decisions
- Maintained the legacy DB trigger projection architecture instead of refactoring it.
- Kept the `tickActions` DAG graph logic strictly intact, modifying only side-effect isolation.
