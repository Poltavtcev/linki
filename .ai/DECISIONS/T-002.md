# T-002: Campaign Engine Adversarial Defects Remediation

## Context
Following the Recovery R3 (T-001), an independent Opus Red Team (RT2) audit was commissioned to find structural blind spots and race conditions. The audit identified 10 potential defects. 

After strict adjudication, 5 targeted execution and concurrency flaws were confirmed as true blockers for Human QA, as they could cause duplicate sends, resurrected unenrollments, and invisible stalled campaigns.

## Confirmed Defects & Fixes

### 1. F-07 & F-08: Tick Resurrection Race
- **Problem**: `tickActions` reads state at the start of the tick, executes slow external side effects (like Playwright `sendMessage`), and then performs a blind update to `state = 'pending'` or `state = 'running'`. If a user unenrolled the profile (or an email bounce occurred) *during* the tick execution, the canonical terminal state was overwritten, resurrecting the profile.
- **Fix**: Added `AND state NOT IN ('completed', 'failed')` to all terminal `tickActions` DB updates (`lib/linkedin/runner.ts`).
- **Validation**: Hostile test `F-07/F-08: Unenroll/Bounce Race Condition` mocks a slow `sendMessage`, unenrolls the profile concurrently, and verifies the state remains `completed`.

### 2. F-01: Email Reply Double-Mutation
- **Problem**: `inbox.ts` properly correlated email replies to exact workflow steps via `outbound_events`. However, it then invoked `ee/index.ts`'s `processReply`, which used a heuristic (`ORDER BY step_order DESC`) to guess the step, blindly overwriting the precise correlation with a potentially incorrect edge.
- **Fix**: Modified `processReply` to check if `rps.current_step_id` already points to an `on_replied` edge. If so, it bails out early, preserving the deterministic correlation.
- **Validation**: Hostile test `F-01: Email Reply Double-Mutation` constructs a divergent DAG where the heuristic chooses Step B but exact correlation chooses Step A, proving the fix retains Step A.

### 3. F-02: processReply Case-Sensitivity
- **Problem**: `ee/index.ts` queried `rps.state IN ('pending', 'running', 'PAUSED')`. Because SQLite strings are case-sensitive, it never matched profiles paused for human approval or uncorrelated replies.
- **Fix**: Changed `'PAUSED'` to `'paused'`.
- **Validation**: Hostile test `F-02: processReply case sensitivity for paused state` proves that a paused profile is correctly resumed.

### 4. F-05: Missing assertLock Fencing
- **Problem**: `assertLock()` was passed to connection requests but completely missing before the `sendMessage` side-effect, allowing a worker that lost its fencing lock to still send a message.
- **Fix**: Passed `assertLock` into `sendMessage()` (`lib/linkedin/runner.ts` and `lib/linkedin/message.ts`) and invoked it immediately before the Playwright `click()` action.
- **Validation**: Hostile test `F-05: Missing assertLock before side-effect` verifies the lock assertion function is properly supplied.

### 5. F-10: Sync Trigger Masks 'paused' State
- **Problem**: The database trigger `sync_run_profile_tracks_state` explicitly mapped the `paused` canonical state to `in_progress` in the UI projection. This made uncorrelated replies and human approval states completely invisible to the user.
- **Fix**: Updated the trigger (`lib/db.ts`) to map `NEW.state = 'paused'` to `'paused'`, ensuring stalled campaigns are visible.
- **Validation**: Hostile test `F-10: Sync Trigger Hides paused state` verifies the UI track state properly reflects `'paused'`.

## Accepted Limitations
- **F-03 (Retry Duplicate Send)**: Retained as an accepted architectural limitation (Finding 2a from R3). The Two Generals Problem exists because Playwright `sendMessage` and SQLite persistence are not atomically linked. If persistence crashes *after* the external side-effect, the engine falls back to a failed state, and a manual retry will cause a duplicate send. T-001 deduplication only protects against duplication if the DB persistence succeeds.

- **Lint/Typecheck**: Passed with no new errors.
